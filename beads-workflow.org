#+TITLE: Beads Workflow — Multi-Agent Coordination
#+OPTIONS: toc:2 num:nil

* Overview

This document defines how the three agents in the workspace use beads issues
and memory to coordinate. Every agent reads from and writes to beads as its
primary communication channel. Direct inter-pane signalling (tmux) is used
only for immediate human-visible alerts.

Test and build commands are a separate channel: tester and developer run
them via =scripts/run_in_watcher.sh=, which submits the command to a
persistent shell in the hidden =runner= window instead of the calling agent's
own Bash tool. This makes the command a real, live process whose output
streams into the Watcher Log as it happens, while still returning the
command's real exit code to the calling agent synchronously. See
=scripts/agents/runner.sh=.

* Issue Types

| Type           | Created by    | Purpose                                              |
|----------------+---------------+------------------------------------------------------|
| =plan-phase=   | Orchestrator  | One unit of work for the developer agent             |
| =test-report=  | Tester        | Results of a test run (pass/fail + details)          |
| =validation=   | Tester        | Signals the user that a feature is ready to review   |

* Status Flow

#+BEGIN_EXAMPLE
open → in_progress → closed
         │
         └── blocked  (needs-refinement: too broad OR too vague, waiting on user)
#+END_EXAMPLE

| Status              | Set by       | Meaning                                              |
|---------------------+--------------+------------------------------------------------------|
| =open=              | Creator      | Ready to be picked up                                |
| =in_progress=       | Agent        | Work has started                                     |
| =blocked=           | Developer    | Step needs refinement before it can proceed          |
| =closed=            | Agent / User | Work is complete                                     |

* Issue Conventions

** plan-phase

A plan has two levels: **phases** (themed groupings, human-facing only, not
beads issues) and **steps** (the atomic dispatchable unit — one =plan-phase=
beads issue per step). See =agents/orchestrator.md= for the full Phase/Step
rules. Created by the user (or orchestrator agent) in the orchestrator pane
— but not until
the full plan has been drafted in conversation and explicitly validated by
the human. The developer agent treats any open =plan-phase= issue as
actionable and picks it up immediately, so issue creation is the point of no
return, not a checkpoint. The orchestrator's session has Edit/Write/
NotebookEdit disabled at the tool level — it can only plan, never implement.
Each issue must:
- Cover changes to at most 2 files — 1 file is the target, not just the ceiling.
- Name the specific file(s) and change, not just the goal — enough that the
  developer agent can implement without asking questions or picking between
  multiple reasonable approaches (except to escalate scope/clarity
  violations, see below).
- Be dispatched explicitly via ="$MULTIAGENTS_ROOT"/scripts/dispatch.sh <issue-id>=.

If the developer finds a dispatched step too broad (>2 files) or too vague
(no single unambiguous implementation), it runs =scripts/notify.sh= to alert
the orchestrator and sets the issue to =blocked= instead of guessing — see
=agents/developer.md=. The orchestrator then rewrites the step's description
and reopens it.

Suggested fields:
#+BEGIN_EXAMPLE
--title="Phase <N>/Step <M>: <short imperative summary>"
--description="What to build and why. File(s): <file1> (<file2>)."
--type=task
--priority=<0-4>
#+END_EXAMPLE

** test-report

Created by the tester agent after each test run. Must include:
- Reference to the =plan-phase= issue it covers.
- Pass/fail status.
- Names of failing tests and error output (if any).

On a FAIL the tester fixes the code itself rather than handing off — there is
no debugger agent. Each debug iteration is appended to this same issue with
=bd update <id> --notes="Root cause: ... Fix: ..."=, so the record of what
broke and why lives with the report instead of in a separate issue.

** validation

Created by the tester agent once all tests pass. Must include:
- References to the original =plan-phase= and final =test-report=.
- Summary of what was built and verified.
- The user closes this issue in the orchestrator pane after manual review.

* Memory Conventions

Agents use =bd remember= to persist knowledge across sessions. Use these
prefixes so entries are searchable:

| Prefix          | Example key                  | What to store                              |
|-----------------+------------------------------+--------------------------------------------|
| =perm:=         | =perm:read:/etc/hosts=       | Granted external file-read authorizations  |
| =agent:=        | =agent:developer:last-phase= | Last issue ID processed by an agent        |
| =pattern:=      | =pattern:test-runner=        | How to run tests in this project           |

Search with: =bd memories <keyword>=

* Dispatch Flow

#+BEGIN_EXAMPLE
User (orchestrator pane)
  │  drafts and refines the plan in conversation — no beads issues yet
  │  once the full plan is explicitly approved:
  │    writes plan-phase issues in beads
  │    runs: "$MULTIAGENTS_ROOT"/scripts/dispatch.sh <issue-id>
  ▼
Developer (top-right pane)
  │  receives issue ID via tmux, marks in_progress
  │  implements feature on the current branch
  │  if scope > 2 files OR the step is too vague to implement without
  │    guessing: scripts/notify.sh → orchestrator, marks blocked
  │  on success: closes plan-phase
  ▼
Tester (bottom-right pane)
  │  detects the new commit
  │  writes + runs unit tests
  │  creates test-report issue (pass or fail)
  │  if fail: fixes the production code itself, commits, re-runs,
  │    appending each iteration to the test-report — until green
  │  creates validation issue
  ▼
User (orchestrator pane)
     reviews validation issue, closes it to confirm or rejects
#+END_EXAMPLE
