* Important Notes

** Prerequisites

This workspace requires an active *Claude subscription plan*. The developer,
tester, and debugger agents each run a persistent Claude Code process — all
three consume API capacity simultaneously.

** What this workspace does (and does not) guarantee

The developer → tester → debugger pipeline is designed to produce code that
passes its own tests and follows the plan you describe in beads issues. It does
*not* guarantee correctness beyond what the tests cover.

** Your responsibility as orchestrator

*Planning is the first and most important part of the work.* Everything
downstream — developer, tester, debugger — executes the plan literally and
in parallel, and the pipeline has no second gate: once a =plan-phase= issue
exists, it is being implemented. A weak plan is not caught later; it is
built. Expect to spend more time in the orchestrator pane refining the plan
than the agents spend implementing it, and treat that as the point, not as
overhead.

*Use the most capable model you have access to for planning.* Decomposition,
spotting ambiguity, and reasoning about how steps interact across files is
exactly where stronger models pay for themselves, and the orchestrator
never writes code, so its token cost is small compared to the three
implementing agents. Inside the orchestrator pane, switch with =/model=:

#+BEGIN_SRC text
/model opusplan   # Opus for plan mode, a faster model for everything else
/model fable      # Fable 5.1, the most capable model, for hard or large plans
#+END_SRC

To make it permanent, add =--model opusplan= (or =fable=) to the =claude=
invocation in =scripts/agents/orchestrator.sh= — only there, so the choice
stays local to the planner. A cheaper model is fine for the implementing
agents; it is a false economy for the planner.

With that in mind, the quality of the output is directly tied to the quality
of your plan:

- *Structure the plan as phases containing steps.* A phase is a themed group
  (human-facing only, not a beads issue); each step inside it is the atomic
  unit that becomes one =plan-phase= beads issue. See =agents/orchestrator.md=.
- *Make each step unambiguous.* If a step can be implemented in more than one
  reasonable way, the agent will pick one — and it may not be the one you had
  in mind. Narrow it until there is only one obvious path. The developer
  agent is required to bounce a vague step back to you (via
  =scripts/notify.sh=) rather than guess — treat that alert as your plan's
  bug, not the developer's.
- *Keep each step small.* At most two files, and one is the target, not just
  the ceiling. Larger steps increase the chance of divergence between your
  expectation and the result.
- *The orchestrator can't write code even if it tried.* Edit/Write/
  NotebookEdit are disabled at the tool level for the orchestrator's Claude
  session (see =scripts/agents/orchestrator.sh=) — it plans, the developer
  implements.
- *Verify and validate every result.* AI tooling can accelerate coding
  significantly, but it can also produce subtly wrong output. Even a
  well-structured, detailed plan does not remove the need for human review.
  Treat agent output as a fast first draft, not a finished product.
- *Don't create the beads issue until the plan is fully validated.* The
  developer agent picks up any open =plan-phase= issue immediately — there is
  no second gate. Discuss and refine the plan in conversation first; only
  once you explicitly approve it should the orchestrator create the issue(s).
  Creating the issue *is* the handoff — the developer's own =bd ready= poll
  picks it up. See =agents/orchestrator.md= for the exact rule.
- *The orchestrator cannot send anything to another agent.* It receives
  messages and talks to you; =dispatch.sh=, =msg.sh= and =notify.sh= refuse to
  run from its pane. Its only write surface is =bd=, and every =bd= write
  needs your approval first. See "The orchestrator is receive-only" below.

* Overview

A reusable tmux-based workspace for multi-agent coding sessions. A single
script call creates a fully laid-out terminal environment where four agents
work together — one human-controlled orchestrator and three autonomous Claude
Code agents — to plan, implement, test, debug, and validate features.

All four agents share the project's working tree and whatever branch you have
checked out. The workspace never creates, switches or rebases branches — if
you want the work isolated on a feature branch, create it yourself before
starting the session (or ask the orchestrator to).

The workspace is designed to be project-agnostic: point it at any directory
and it sets up the same consistent layout every time.

* Layout

One tmux session, one window, four panes arranged in a 2×2 grid:

#+BEGIN_EXAMPLE
┌─────────────────────┬─────────────────────┐
│                     │                     │
│    orchestrator     │     developer       │
│     (you)           │   (Claude Code)     │
├─────────────────────┼─────────────────────┤
│                     │                     │
│      tester         │     debugger        │
│   (Claude Code)     │   (Claude Code)     │
└─────────────────────┴─────────────────────┘
#+END_EXAMPLE

| Pane          | Role                                                                   |
|---------------+------------------------------------------------------------------------|
| orchestrator  | You + Claude. Draft and validate the plan in conversation first; only  |
|               | once it's fully approved are beads issues created. Sends nothing       |
| developer     | Implements one plan phase at a time, no tests                          |
| tester        | Writes and runs unit tests for each new feature                        |
| debugger      | Fixes failing tests, iterates with tester                              |

There is also a hidden fifth window, =runner= (not part of the 2×2 grid —
switch to it with tmux's window list, =C-b w=). It's a persistent shell that
tester/debugger/developer route test and build commands through (via
=scripts/run_in_watcher.sh=) instead of running them inside their own Claude
session's Bash tool, so the output is a real live process that streams into
the Watcher Log as it happens, not something buried invisibly until a whole
Claude turn finishes. See =scripts/agents/runner.sh=.

* Workflow

#+BEGIN_EXAMPLE
You (orchestrator, tab 1)
  │  1. Draft the plan as phases, each broken into steps
  │     (no beads issues yet — you cannot edit files, only plan)
  │  2. Once you explicitly approve the full plan, one plan-phase
  │     beads issue is created per step (≤ 2 files, 1 ideal)
  │  3. Nothing is dispatched — the developer's bd ready poll
  │     picks the open issue up within 30s
  ▼
Developer (tab 2)
  │  Reads the issue, implements the feature, commits
  │  If scope > 2 files OR the step is too vague → notifies you and waits
  │  On success → closes the issue
  ▼
Tester (tab 3)
  │  Detects the new commit
  │  Writes unit tests, runs them
  │  Creates a test-report beads issue (PASS or FAIL)
  ▼
Debugger (tab 4)
  │  If FAIL → fixes code, signals tester to rerun, iterates
  │  When all tests pass → creates a validation beads issue, notifies you
  ▼
You (orchestrator, tab 1)
     Review, close the validation issue to confirm, or reject
#+END_EXAMPLE

See =beads-workflow.org= for the full coordination protocol.

* Installation

** Two-repo mental model

=multiagents-setup= is a standalone tool — it lives in its own git repository
and is installed once. It is *never* cloned inside your project. Think of it
the same way you think of =vim= or =make=: the tool lives elsewhere on your
machine, and you invoke it from whichever project you want to work on.

#+BEGIN_EXAMPLE
~/ (or any stable location)
└── multiagents-setup/       ← tool repo, cloned once, never touched by agents
    ├── workspace.sh
    ├── agents/
    ├── scripts/
    └── .beads/              ← coordination layer, separate from your project

/path/to/your-project/       ← your project repo, unchanged
                             ← all four agents work here, on the branch you
                                have checked out
#+END_EXAMPLE

This separation means:
- Agents can never accidentally commit tooling files into your project.
- Your project's git history stays clean.
- The workspace works with any project without any setup inside that project.

** Clone the tool

#+BEGIN_SRC sh
git clone <multiagents-setup-repo-url> ~/multiagents-setup
#+END_SRC

Clone it to a stable location. Do not move it afterwards — the alias below
will point to this path.

** Install prerequisites

=setup.sh= checks for =tmux= and =bd= (beads) and installs whichever is
missing. It also reports on =git=, =bash= and the =claude= CLI, which it does
not install.

#+BEGIN_SRC sh
~/multiagents-setup/setup.sh            # prompts before installing anything
~/multiagents-setup/setup.sh --check    # report only, exit 1 if something is missing
~/multiagents-setup/setup.sh --dry-run  # print the install commands without running them
~/multiagents-setup/setup.sh --yes      # non-interactive (CI, provisioning scripts)
#+END_SRC

Everything is installed into user space; =sudo= is never needed. =tmux= comes
from conda-forge when conda/mamba/micromamba is present: it goes into a
dedicated =multiagents-tools= env (name set by =MULTIAGENTS_CONDA_ENV= in
=config/workspace.conf=) which =workspace.sh= activates automatically whenever
conda and that env exist, so every agent pane sees it; a symlink in
=~/.local/bin= also makes =tmux attach= work from a plain shell. Without
conda, =tmux= comes from Homebrew when =brew= is present, and otherwise as a
static Linux x86_64 binary in =~/.local/bin=. =bd= is installed with the official beads installer into
=~/.local/bin=. Set =TMUX_INSTALL_METHOD= (=conda=, =brew=, =static=, or =pkg=
for the system package manager, which does need sudo) or =BEADS_INSTALL_METHOD=
(=script=, =brew=, =npm=, =go=) to force a method. Make sure =~/.local/bin= is
on your =PATH=; the script tells you if it is not.

** Add a shell alias

Add this to your =~/.zshrc= or =~/.bashrc=:

#+BEGIN_SRC sh
alias workspace="~/multiagents-setup/workspace.sh"
#+END_SRC

Reload your shell:

#+BEGIN_SRC sh
source ~/.zshrc   # or ~/.bashrc
#+END_SRC

You now have a =workspace= command available from anywhere.

* Usage

** IMPORTANT: always run from inside your project

=workspace.sh= must be run from the root of the project you want to work on,
not from inside the =multiagents-setup= directory.

#+BEGIN_SRC sh
cd /path/to/your-project
workspace
#+END_SRC

This is because:
- =WORKSPACE_DIR= defaults to =$(pwd)=, so the agents are rooted in your project.
- All git commands the agents run operate on the repo in the current
  directory, which must be your project — not the tooling repo.
- The tooling scripts resolve their own location via =SCRIPT_DIR= at runtime,
  so they are always found correctly regardless of where you invoke them from.

Running =workspace.sh= from inside =multiagents-setup/= itself would point the
agents at the wrong repository.

** Start the workspace

#+BEGIN_SRC sh
cd /path/to/your-project
workspace
#+END_SRC

Opens a session named =multiagents= rooted in the current directory.
The developer, tester, and debugger agents start automatically in their panes.

** Custom session name

#+BEGIN_SRC sh
workspace -s myproject
#+END_SRC

Or via environment variable:

#+BEGIN_SRC sh
SESSION_NAME=myproject workspace
#+END_SRC

** Attach to an existing session

#+BEGIN_SRC sh
workspace --attach
workspace -s myproject --attach
#+END_SRC

** Full option reference

#+BEGIN_EXAMPLE
Options:
  -s, --session NAME    Session name (default: multiagents)
  -d, --dir DIR         Working directory (default: current directory)
  -a, --attach          Attach to existing session if it exists
  -h, --help            Show this help
#+END_EXAMPLE

** How an approved phase reaches the developer

Creating the =plan-phase= beads issue *is* the handoff. Every agent with
nothing to do parks in =scripts/idle_wait.sh=, re-checking =bd ready= every 30
seconds, so an open, unblocked issue is picked up on the next cycle with
nothing typed into its pane. The developer implements it on the current branch
and triggers the rest of the pipeline automatically.

Two corollaries:

- A free-form message with no beads issue behind it gives that poll nothing to
  find, and the pane then looks like it never started. Work goes out as an
  issue, never as text.
- Never flip an issue to =in_progress= yourself: =bd ready= excludes
  =in_progress=, which hides it from the very poll that delivers it. The
  developer claims it when it actually starts.

=dispatch.sh <issue-id>= still exists for *you* to nudge the developer to look
sooner (from your own terminal, not from the orchestrator pane — see below);
it is a nudge, never the delivery mechanism.

#+BEGIN_SRC sh
~/multiagents-setup/scripts/dispatch.sh <issue-id>
# example:
~/multiagents-setup/scripts/dispatch.sh myproject-abc
#+END_SRC

** The orchestrator is receive-only

The orchestrator plans and talks to you. It can *receive* messages from the
other agents (=[MSG from ...]=, and =[AGENT ALERT]= via =notify.sh=), but it
cannot send anything to anyone:

- =dispatch.sh=, =msg.sh= and =notify.sh= each check the calling pane's =@role=
  stamp and exit with an error when it is =orchestrator=. The check lives in
  =scripts/sender_guard.sh=, shared by all three, with no environment escape
  hatch — an env var the orchestrator could set itself would not be a block.
- File mutation is already off at the tool level (=--disallowed-tools
  Edit,Write,NotebookEdit= in =scripts/agents/orchestrator.sh=). Its only write
  surface is =bd=, and =agents/orchestrator.md= requires your explicit approval
  in the conversation before any =bd= write that creates or reopens work.

Why: text the orchestrator sends is invisible to you in detail, yet lands in
the recipient as an instruction it acts on, outside the plan you approved —
which has created new problems instead of solving the original one. If
something must be said to another agent, the orchestrator tells you the exact
wording and *you* send it with =msg.sh= from your own terminal.

** Idle agents and the 30-second wait loop

An agent with nothing to do parks inside one blocking call to
=scripts/idle_wait.sh <role>=, which re-checks its own trigger — =bd ready=
for the developer, new commits for the tester, open test reports for the
debugger — every 30 seconds for 15 cycles, then returns and is re-run.

The loop lives in a script rather than in the agent's prompt on purpose. An
instruction like "check every 30 seconds" makes each iteration a whole model
turn, which costs far more than 30 seconds and is not bounded by anything, so
the real cadence silently drifts into minutes.

While an agent is parked there, it is inside a tool call: text typed into its
pane only queues until that call returns. So each wait iteration stamps a
heartbeat file (=$TMPDIR/multiagents-<session>/<role>.idle=), and
=dispatch.sh=/=msg.sh= interrupt the pane — Escape, claude's own interrupt —
when that heartbeat proves it is merely sleeping. A pane doing real work is
never interrupted, so a message to a busy agent still waits for its current
turn to end. Tune the cadence with =AGENT_IDLE_INTERVAL= and
=AGENT_IDLE_CYCLES= if needed.

** Messaging an agent directly

Available to you and to the developer, tester and debugger panes — not to the
orchestrator, which is blocked from every send path (see above).

=dispatch.sh= and =notify.sh= cover the two fixed edges of the routine
pipeline. Everything else — one agent asking another a specific, off-script
question, or you poking a single pane from a shell — goes through =msg.sh=:

#+BEGIN_SRC sh
~/multiagents-setup/scripts/msg.sh <role> "<message>"
# example:
~/multiagents-setup/scripts/msg.sh tester "Which fixture does test_auth_flow use?"
#+END_SRC

=<role>= is =orchestrator=, =developer=, =tester=, or =debugger=. The recipient
pane is resolved by its =@role= stamp, and the message arrives tagged
=>>> [MSG from <sender>]= — the sender being the role of the pane the script
was called from, or =user= when called from a plain terminal.

Messages carry questions; work still moves through beads issues, so pipeline
state survives a pane restart.

* Keybindings

| Key     | Action                                                       |
|---------+---------------------------------------------------------------|
| =C-q=   | Stop every agent process and the watcher, then kill the session |
| =C-b d= | Detach from the session (agents keep running)                |

Standard tmux navigation (=C-b= prefix) works as usual for switching panes,
resizing, scrolling, etc.

=C-q= runs =scripts/quit_workspace.sh=, which force-stops each pane's restart
loop and its =claude= child (not just the tmux pane) before killing the
session. None of the launch scripts ever pass =--continue= or =--resume=, so
quitting never leaves a Claude session to resume from — reattaching to a
workspace is =workspace --attach= (tmux session persistence), not a Claude
resume prompt. Detaching with =C-b d= is different: it leaves everything
running in the background — see "Detaching and Reattaching" below.

* Detaching and Reattaching

Detaching leaves the session and all agents running in the background.

** Detach

#+BEGIN_SRC sh
C-b d          # keyboard shortcut inside the session
tmux detach    # command line equivalent
#+END_SRC

** Reattach

#+BEGIN_SRC sh
tmux attach-session -t multiagents
tmux a -t multiagents            # short form
./workspace.sh --attach          # via the workspace script
#+END_SRC

** List running sessions

#+BEGIN_SRC sh
tmux ls
#+END_SRC

* Requirements

Run =./setup.sh= to check and install these (see Installation).

- =tmux= ≥ 2.6 (for =select-pane -T= pane title support)
- =bash= ≥ 4.0
- =claude= CLI (Claude Code) — installed and authenticated
- =bd= (beads) — issue tracker used for all agent coordination

** Beads quick reference

Run =bd prime= at the start of any session for full context.

| Command                    | Purpose                        |
|----------------------------+--------------------------------|
| =bd prime=                 | Load session context           |
| =bd ready=                 | Show issues ready to work on   |
| =bd create --title="..."=  | File a new issue               |
| =bd update <id> --claim=   | Claim an issue                 |
| =bd close <id>=            | Mark an issue complete         |
| =bd remember "insight"=    | Persist a note across sessions |
| =bd memories <keyword>=    | Search persistent memory       |

* Extending the Workspace

1. Add a new =PANE_*= variable in =config/workspace.conf=.
2. Add the corresponding split and title call in =workspace.sh=.
3. Create =agents/<role>.md= with the agent's instructions.
4. Create =scripts/agents/<role>.sh= to launch Claude Code with that file.
5. Wire the launch command into =workspace.sh= for the new pane.
